# Endpoint 콜드스타트 측정, 네트워크 바닥 분리, `D4` 지연 결론 정정

## Scope

`G0`의 Endpoint 항목을 측정하고, 그 과정에서 드러난 네트워크 왕복 비용을 분리해
attempt-004의 `D4` 결론을 재검증했다. 공개 SO-101 데이터셋도 조사했다.

**하지 않은 것**: ACT 학습 미착수, GPU 잡 미실행, 실기 없음.

## Endpoint 콜드스타트 (`D6`)

`python:3.12-slim`에 `python -m http.server` — **연산이 사실상 0인** 컨테이너.
토큰 인증을 걸어 생성하고 측정 후 삭제했다 (`--auth` 기본값이 `none`이라 그대로 두면 열린다).
측정 종료 후 잔여 엔드포인트 0개를 확인했다.

| 지표 | 값 |
|---|---|
| create 호출 | 9.2s |
| create → URL 확보 | 72s |
| create → **최초 성공 응답** | **119s** |
| 웜 왕복 (중앙값 / p90 / 최대) | **854ms** / 906ms / 928ms |

## 네트워크 바닥을 분리했다 — 이게 핵심 발견

웜 지연 854ms가 **디렉토리 리스팅만 하는 컨테이너**에서 나왔다. 연산이 0인데 854ms면
대부분이 네트워크·터널 비용이라는 뜻이다. 호스트별 왕복을 직접 쟀다 (5회 중앙값).

| 호스트 | TCP connect | TLS 완료 | 전체 |
|---|---|---|---|
| `api.studio.nebius.com` (Token Factory) | **315ms** | 624ms | 931ms |
| `api.nebius.cloud` (Cloud API) | 6ms | 27ms | 288ms |
| `huggingface.co` | 15ms | 29ms | 59ms |

**Token Factory가 물리적으로 멀다.** TCP RTT 315ms가 바닥이고, 새 연결마다 TLS
핸드셰이크로 624ms를 더 쓴다. Cloud API(6ms)와 대조하면 경로가 완전히 다르다.

## `D4` 결론 정정

attempt-004에서 "`D4`의 2Hz는 현재 구성으로 불가능하다 — MiniCPM-V 중앙값 1000ms,
예산의 2.0배"라고 기록했다. **그 측정은 요청마다 새 TLS 연결을 맺었다.**
런타임 감독자는 같은 연결을 계속 쓰므로 운영 조건과 맞지 않는 측정이었다.

연결 재사용(keep-alive)으로 재측정한 결과:

| 모델 | 연결 수립 | 이후 요청 중앙값 | 범위 | 2Hz 예산(500ms) |
|---|---|---|---|---|
| `openbmb/MiniCPM-V-4_5` | 650ms | **381ms** | 376–414 | **예산 내** |
| `google/gemma-3-27b-it` | 606ms | 739ms | 453–968 | 1.5배 초과 |

**`D4`의 2Hz는 MiniCPM-V + 연결 재사용이면 달성 가능하다.** attempt-004의 반대 결론을
철회한다. 다만 조건이 붙는다.

- 마진이 얇다. 381ms 중 **약 315ms가 네트워크 RTT**이고 우리가 통제할 수 없는 부분이다.
  서버 연산은 약 66ms에 불과하므로, **모델을 더 빠른 것으로 바꿔도 개선 여지가 거의 없다.**
  경로가 나빠지면 그대로 예산을 넘는다
- `gemma-3-27b-it`은 분산이 크다(453–968ms). 안전 판정 경로에는 부적합하다
- n=6이라 꼬리 지연을 말할 수 없다. MiniCPM-V의 범위가 376–414로 좁은 것은 좋은 신호지만
  표본이 적다

따라서 **연결 유지를 사양에 명시**하고, attempt-004에서 제안한 비동기 구조는
폐기가 아니라 **안전망으로 유지**하는 것이 맞다.

## `D6`에 대한 함의

- **콜드스타트 119s는 런타임에 지불하지 않아도 된다.** 엔드포인트를 실기 세션 전에 미리 띄우면
  된다. §12의 완화책 "웜 상태 유지"가 유효하다
- 다만 **웜 상태에서도 왕복 854ms**가 든다. GR00T 추론 시간은 여기에 더해진다.
  폴백은 스텝 단위 제어 루프가 될 수 없고, **액션 청크 단위**여야 한다.
  ACT의 chunk 100 @ 30fps ≈ 3.3초 분량이므로 청크 단위면 성립한다
- 이 854ms는 eu-west1 터널 기준이다. GR00T를 어느 리전에 띄우느냐로 달라진다

## 공개 SO-101 데이터셋 (`G0` 항목)

`lerobot/svla_so101_pickplace` (공식)

| 항목 | 값 |
|---|---|
| robot_type | `so100_follower` (SO-100/101 동일 6-DoF 레이아웃) |
| codebase | v3.0 |
| 에피소드 / 프레임 | 50 / 11,939 (30fps, 에피소드당 약 8초) |
| observation.state / action | 각 6차원 (shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, …) |
| 카메라 | `observation.images.up`, `observation.images.side` — 각 480×640×3 |

**attempt-003에서 만든 ACT 그래프의 가정과 정확히 일치한다** (카메라 2대, state 6, action 6,
480×640). `G0` 드라이런을 무작위 데이터가 아니라 실데이터로 다시 돌릴 수 있다.

후보 하나 더: `777im/so101_pick_plug_insert_v5_v6`은 **플러그 삽입** 태스크로
§2.1의 슬롯 삽입과 태스크 성격이 가장 가깝다. 캘리브레이션 구성 축(`calib_composition`)의
"복구 궤적 포함" 같은 구분을 실데이터로 연습해볼 수 있는지 확인할 가치가 있다.

## Verification

- 엔드포인트는 **연산이 0인 컨테이너**로 쟀다. GR00T를 올렸을 때의 콜드스타트는
  이미지 크기와 모델 로딩 때문에 **119s보다 훨씬 길 것이다.** 이 값은 하한이다
- `D4` 재측정은 n=6, 단일 세션, 합성 프레임이다. 시간대·경로 변동을 반영하지 않는다
- 네트워크 왕복은 이 머신(GB10)에서 잰 값이다. 실기 때 Jetson이 어느 네트워크에 붙느냐에
  따라 달라진다. **Jetson에서 재측정해야 `D4`/`D6` 사양을 확정할 수 있다**
- SO-101 데이터셋은 메타데이터만 조회했다. 실제 다운로드·로딩은 하지 않았다

## 주장하지 않는 것

- `D4`가 2Hz로 **정확한 판정**을 한다고 말하지 않는다. 측정한 것은 지연뿐이다
- 콜드스타트 119s가 GR00T에도 적용된다고 말하지 않는다
- SO-101 데이터셋으로 학습한 ACT가 쓸 만하다고 말하지 않는다. 형상이 맞는다는 것만 확인했다
