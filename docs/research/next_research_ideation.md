# 다음 연구 아이데이션 — 다중 가속기 배포 검증과 Safety Robotics (2026-10-16)

QuantGate(해커톤)와 AEP 이후의 연구 후보를 정리한 내부 문서. 아직 사전등록 전이다. 실험을 시작할 때 항목별로
사전등록 문서를 따로 만든다.

**핵심 관찰.** "어느 양자화 빌드가 좋은가"의 답이 **가속기·컴파일러·실행 경로마다 달라진다.** 그래서 한 장치에서
내린 판정을 다른 장치로 옮겨 쓸 수 없다. 이것이 AEP의 주장("측정한 실행 파일을 실제 실행 경로에서 검증하라")을
물리 로봇과 여러 가속기로 넓히는 출발점이다.

## 1. 하드웨어와 툴체인

| 장치 | 연산부 | 툴체인 | 정책 실행 | 비고 |
|---|---|---|---|---|
| Jetson Orin Nano Super | GPU, 15 W | TensorRT 10.3 + ModelOpt | 전체 그래프 (FP32/FP16/INT8) | 기준 장치. 실기 505회 |
| Raspberry Pi 5 + Hailo-8 | NPU 26 TOPS + CPU | Hailo DFC 3.34 (kepler에서 컴파일) + HailoRT 4.20 | 백본만 NPU, Transformer는 CPU | 마감 초과. DFC는 보정 데이터로 양자화 미세조정(QAT 계열)을 함 |
| **Arduino VENTUNO Q** (확보) | Qualcomm Dragonwing IQ8 (NPU 40 TOPS) + **STM32H5 MCU** | **QAIRT** (Qualcomm AI Runtime: QNN 계열 converter·quantizer·context binary) + **AIMET** (CLE, AdaRound, QAT) | 전체 그래프를 NPU에 올릴 수 있는지가 첫 질문 | MCU가 실시간 제어 담당 → 안전 감시 계층에 적합 |
| **Coralboard** (다음 주) | Coral NPU 1 TOPS, 초저전력 | 초기 단계 툴체인 (받은 뒤 지원 형식 확인) | ACT 전체는 어려울 가능성 큼 | 상시 감시 모델용 |
| GX10 (GB10) | 데스크톱 GPU | Isaac Sim 6.2 | HIL 영상 생성, 대량 시뮬레이션 | 트윈 |

**QAIRT 메모.**
- 흐름: ONNX → converter → quantizer(보정 데이터, W8A8 또는 W8A16, per-channel 등) → NPU용 context binary
  → 장치 실행(net-run 계열 도구 또는 런타임 API).
- 정확한 도구 이름과 옵션은 설치한 SDK 버전에서 다시 확인한다. 버전마다 이름이 다르다.
- **AIMET의 AdaRound는 AEP가 시뮬레이션에서 다룬 개입과 같다.** AEP에서는 8개 규칙 모두 RMSE가 줄었지만 평균
  반환은 5개에서 감소했다. 같은 개입을 실제 로봇에서 재현할 수 있다(→ 아이디어 B).
- Hailo처럼 일부 연산(LayerNorm, Attention 등)이 NPU에 안 올라갈 수 있다. 그래서 첫 단계는 언제나 **이식성 점검**이다:
  오프라인 출력 차이, 지연, 200 ms 마감.

## 2. 아이디어 (우선순위 순)

### A. 가속기 간 판정 이전성 (AEP 물리 확장) — 1순위

**질문.** 같은 ACT 체크포인트를 Jetson(TensorRT), Hailo-8(DFC), VENTUNO Q(QAIRT)로 양자화했을 때:
1. 보정 선택(프레임 수, 구성, per-tensor/per-channel)의 효과가 가속기 사이에서 같은 방향인가?
2. 각 가속기의 오프라인 충실도(행동 오차)가 그 가속기의 폐루프 성공·배치 오차를 예측하는가?
3. 한 가속기에서 "검증 우선 후보"였던 빌드가 다른 가속기에서도 그런가?

**설계.**
- **같은 보정 격자:** 16/128/1024 프레임 × 성공 시연만/후반부만 × per-tensor/per-channel. 가속기마다 지원하는 범위
  안에서 맞춘다.
- **같은 감사:** 보류 상태 2,000개, 장치에서 직접 실행한 출력으로 측정한다(에뮬레이터 아님). 순위는 실기 전에 봉인한다.
- **폐루프:**
  1. Isaac Sim 트윈 HIL: 트윈이 카메라 영상을 만들어 **각 보드의 실제 엔진**에 보내고, 엔진의 행동을 트윈에 돌려준다.
     빌드마다 수백 회를 돌린다.
  2. 그중 사전등록된 소수 후보만 실제 SO-101에서 봉인·인터리브 블록으로 확인한다.
- **판정:** QuantGate 규칙을 쓰되, 천장 규칙을 개정해 사전등록한다(`next_test_plans.md` 참고).

**가설(사전등록 후보).**
- H1: 보정 효과의 방향은 가속기 사이에서 일치하지 않는다. Hailo에서 이미 한 번 관찰했다.
- H2: 가속기 안에서도 오프라인 충실도의 순위가 폐루프 순위를 예측하지 못한다(AEP).

**전제 조건.**
- 트윈의 시뮬레이터–실제 결과 일치도가 먼저 확인돼야 한다(진행 중인 14개 rollout 시험).
- 일치도가 낮으면 트윈 결과는 후보 선별용으로만 쓴다.

**산출물.** AEP 후속 논문의 물리 근거, QuantGate의 다중 장치 판정.

### B. AIMET AdaRound / CLE 개입의 실기 재현 — 1.5순위 (A의 하위 실험)

- **질문:** RMSE를 줄이는 컴파일러 개입이 실기 성공을 높이는가, 낮추는가?
- **설계:** 같은 보정 데이터로 QAIRT 기본 양자화, CLE, AdaRound, AdaRound+CLE 네 빌드를 만든다. 오프라인
  RMSE와 실기·트윈 성공을 비교한다.
- AEP 시뮬레이션 결과(RMSE는 8/8 감소, 반환은 5/8 감소)가 **실제 로봇 조작 과제**에서도 나오는지가 핵심이다.
- 비용이 작고 결과의 메시지가 분명하다. A의 첫 블록으로 적합하다.

### C. "두 개의 뇌" 런타임 보증 (VENTUNO Q) — Safety Robotics 핵심 과제

- **구조 (Simplex 계열):**
  - NPU: 학습 정책 (ACT)
  - STM32H5 MCU: 검증 가능한 단순 안전 감시자. 관절 한계와 속도·가속 범위, chunk 마감(200 ms) 감시, 출력 이상값
    (NaN, 점프), 센서 정지 감지를 맡고, 위반 시 안전 정지하거나 쉬는 자세로 복귀시킨다.
  - (선택) Coralboard: 정책과 다른 하드웨어·모델로 카메라를 상시 감시(→ D)
- **실험:** 사전등록한 결함 주입.
  - 늦은 chunk, 정규화 파일 교체, NaN 주입, 카메라 정지, 한 관절의 명령 폭주
  - 사람 손 진입(트윈에서 먼저 시험하고, 실기는 안전 장치를 갖춘 뒤)
- **지표:** 결함별 감지율과 오경보율, 결함 발생부터 정지까지의 시간(MCU 주기 단위), 정상 trial의 성공률 손실
  (감시자가 너무 보수적이지 않은지).
- **QuantGate와의 연결:** 배포 전 점검(엔진 해시, 정규화 매니페스트, 마감)을 **실행 중 감시**로 옮긴다. 이번 Hailo
  사례(마감 초과)는 MCU 감시자가 실시간으로 잡아야 할 결함의 실제 예다.
- **표준과의 연결:** 기능 안전에서 말하는 "독립적 감시 채널"의 학습 정책 버전이다. ISO 10218 / ISO/TS 15066 맥락에서
  설명할 수 있다.

### D. 독립 상시 감시자 (Coralboard) — C와 묶음

- **역할:** 저전력 상시 감시. 작업 영역 침입(사람 손), 캔 낙하·넘어짐, 팔이 정해진 공간을 벗어나는지를 본다.
- **검증 절차:** Cosmos 판정기와 같은 방식으로 한다.
  1. 개발 집합에서 프롬프트·임계값을 정한다.
  2. 보류 집합에서 감지율과 오경보를 잰다.
  3. 새 실기에서 전향적으로 다시 확인한다.
- 녹화 데이터 505회와 LabLens 묶음을 학습·검증 데이터로 쓴다.
- **다양성 중복:** 정책(Qualcomm NPU)과 감시자(Coral NPU)가 서로 다른 하드웨어·모델이라 공통 원인 고장에 강하다.
  이 가설 자체를 결함 주입으로 확인한다.
- **위험:** 한정판이라 툴체인이 초기 단계일 수 있다. 받으면 1주 안에 "작은 분류기 하나가 30 Hz 근처로 도는가"부터
  확인하고, 안 되면 Jetson의 작은 모델로 대체한다.

### E. 지연을 안전 변수로 다루기 (Hailo·QAIRT 공통)

- **질문:** 추론이 마감을 넘을 때 행동은 어떻게 바뀌는가? 미리 요청하는 스텝을 늘리면 늦은 chunk가 사라지는 대신,
  더 오래된 관측으로 행동하게 된다. 어느 쪽이 위험한가?
- **설계:**
  - 미리 요청 스텝 10/14/20(마감 200/333/533 ms)과 인위적 지연 주입을 교차한다.
  - 트윈에서 먼저 하고, Hailo 분할 실행(239 ms)과 QAIRT 빌드를 실제 사례로 쓴다.
- **산출물:** "이 정책은 지연 X ms까지 성공률을 유지한다"는 지연 허용 범위. 배포 전 점검의 마감 값을 근거 있게 정할 수
  있다.
- 이번 리뷰에서 지적된 "실행 경로가 바뀌면 행동이 바뀐다"를 정량화하는 실험이다.

### F. Hailo 그림자 실행 → QAIRT로 확장

- **방식:** 팔은 Jetson이 움직이고, 같은 관측을 Hailo와 VENTUNO Q에 보내 행동만 계산·기록한다. 그림자 실행이라
  안전 위험이 없다.
- **얻는 것:** 실제 rollout 상태에서 장치별 출력 차이. 고정 상태 2,000개와 실제 방문 상태가 다르다는 문제(on-policy
  격차)를 측정한다.
- 비용이 작다. A의 오프라인 감사를 보완하는 근거가 된다.

### G. on-policy 감사와 증류 (장기)

- 505회 실기에서 실제로 방문한 상태를 FP32 교사로 라벨링한다.
  1. 그 상태로 감사 점수를 다시 매긴다.
  2. NPU별 양자화 인식 미세조정을 한다(DAgger, FP32를 전문가로).
- 교사와 학생의 차이만 줄일 수 있다는 한계(시작 위치 약점처럼 교사도 가진 약점은 못 고친다)를 명시한다.

## 4. 공통 원칙 (QuantGate에서 가져갈 것)

- 사전등록 → 봉인·인터리브 일정 → 해시 고정 → 봉인 해제 → 사전등록 분석. 사후 분석은 따로 표시한다.
- 비용과 출력은 **대상 장치에서 측정한 실행 파일로** 잰다. 에뮬레이터 결과는 참고로만 쓴다.
- 성공률 기준 통과와 최종 GO를 구분한다(배치 오차, 천장 규칙, 배포 전 점검).
- AI 감시자는 검증 대상 부품으로 다룬다. 보류 집합 → 전향적 재확인 순서다.
- 시험 규모는 미리 검정력으로 계획한다. 천장 규칙처럼 규모와 무관하게 판정을 막는 규칙이 있는지 먼저 확인한다.

## 5. 위험과 미정 사항

- **QAIRT·Coral 툴체인의 연산 지원:** ACT의 Transformer 부분이 NPU에 안 올라가면 Hailo처럼 분할 실행이 되고, 지연
  문제가 반복된다. 이 경우 Transformer 경량화나 양자화를 별도 과제로 둔다.
- **트윈 일치도:** 일치도가 낮으면 A의 대량 시험을 트윈에 맡길 수 없다. 그 경우 실기 규모를 키우거나 질문을 오프라인
  쪽으로 좁힌다.
- **실기 시간:** 실기 1회는 약 1.5분이다. 팔당 120회 × 여러 빌드는 현실적으로 어렵다. 그래서 트윈으로 거른 뒤
  소수만 실기로 확인하는 구조가 필수다.
- **안전 결함 주입의 실기 안전:** 사람 손 진입 같은 시나리오는 트윈에서만 하거나, 물리적 차단 장치를 갖춘 뒤에 한다.
