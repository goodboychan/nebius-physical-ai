## 1. S3 서비스 계정 접근 키

**왜 사람이**: 장기 자격증명 생성은 되돌리기 번거롭고 권한 범위 결정이 필요하다.

**왜 필요한가**: `G4`에서 감사 팬아웃이 2,000상태 × 26셀의 오차 벡터를 잡에 넘겨야 한다.
`--inject-file`은 전체 합계 64 KiB 한도라 불가능하고(`docs/tool_feedback.md` 3번),
`--volume s3://BUCKET:/path`가 유일한 경로다. 버킷 `edgeqgate-audit`은 이미 만들어져 있다.

**권장 절차** (CLI 기준, 콘솔로 해도 동일):

```bash
export PATH="$HOME/.nebius/bin:$PATH"
PROJ=project-e01f64hqpa00n30sz1jybm

# (1) 전용 서비스 계정. 기존 mlflow-sa에 붙이면 권한 범위가 섞인다
nebius iam v1 service-account create --parent-id $PROJ --name edgeqgate-audit-sa

# (2) 접근 키. mystery_box 모드면 비밀이 stdout에 나오지 않고 저장소로 들어간다
nebius iam v2 access-key create \
  --parent-id $PROJ \
  --name edgeqgate-audit-s3 \
  --account-service-account-id <위에서 나온 serviceaccount-...> \
  --secret-delivery-mode mystery_box \
  --expires-at 2026-11-30T00:00:00Z

# (3) 확인
nebius mysterybox secret list --parent-id $PROJ
```

**권고 사항**

- `--secret-delivery-mode mystery_box`를 쓸 것. `inline`은 비밀이 응답에 실려 나와
  파일로 남는다
- `--expires-at`을 **반드시** 지정할 것. 제출 마감이 2026-10-30이므로 11-30이면 충분하다
- 권한은 버킷 `edgeqgate-audit` 읽기/쓰기로 한정할 것

**잡에서 쓰는 법**

```bash
nebius ai job create ... \
  --volume s3://edgeqgate-audit:/data:ro:default@<SECRET_NAME>
```

`--volume` 도움말의 *"For S3 MysteryBox auth use PROFILE@SECRET_SELECTOR"* 경로다.

**완료 후 알려줄 것**: secret 이름(또는 secret ID). 비밀값 자체는 필요 없다.

## 2. §7.3 `ES` 커버리지 갭 결정

**왜 사람이**: 엔드포인트 정의 변경은 사전등록의 핵심이며 에이전트가 정할 사안이 아니다.

**문제**: §7.1의 arm 표는 `score_align` 기준으로만 셀을 고른다. §7.3의 `ES-1`은
`score_mag` 상위 3셀, `ES-2`는 `score_cheap_A` 상위 3셀, `ES-3`은 `score_cheap_B`
상위 3셀의 성공률을 요구하는데, 그 셀들이 어느 arm에도 없으면 **실기 데이터가 0개라
계산 불가**다.

### 비용 정량화 (attempt-020)

점수 간 순위 상관을 주입해 3,000회 시뮬레이션했다 (Spearman 검증: 0.8→0.81, 0.95→0.96).

| `score_mag`의 `score_align` 상관 | 추가 필요 셀 평균 | p90 | 이미 충족 |
|---|---|---|---|
| 0.0 (무상관, 최악) | 5.40 | 7 | 0.0% |
| 0.8 | 4.64 | 6 | 0.0% |
| 0.95 (거의 동일) | 4.01 | 5 | **0.1%** |

**상관이 0.96이어도 커버리지가 저절로 충족되는 경우는 0.1%다.** 이 문제는
"운이 좋으면 넘어갈 수 있는" 종류가 아니다.

### 누락의 출처 분해 (상관 0.8 기준)

| 출처 | 평균 누락 셀 | p90 | 전혀 누락 안 됨 |
|---|---|---|---|
| **`score_cheap_A`** | **2.06** | 3 | 2.2% |
| `score_cheap_B` | 1.92 | 3 | 3.9% |
| `score_mag` | 1.28 | 2 | 14.0% |

**최대 기여자는 `score_cheap_A`이고, 그 상위 3셀은 데이터와 무관하게 오늘 이미
확정되어 있다** — `VC-020` / `VC-022` / `VC-024` (calib_size 1024 × per-channel × 구성 3종).
데이터를 보지 않는 고정 휴리스틱이기 때문이다.

### 선택지와 비용

| 선택지 | 추가 trial | 총계 | 얻는 것 |
|---|---|---|---|
| **(1) `cheap_A` 3셀만 보장** | +30 (셀당 10) | 255 (+13%) | **`ES-2`가 확정적으로 계산 가능** |
| (2) 전면 보장 | +60–90 | 285–315 (+27~40%) | `ES-1`/`ES-3`까지, 단 p90 기준이라 불확실 |
| (3) 예산 225 고정, 재배분 | 0 | 225 | `EP-1` 표본 75 → 45. **검정력 0.65에서 더 떨어진다** |
| (4) 엔드포인트 재정의 | 0 | 225 | trial 있는 셀로 제한한 순위 비교. 주장이 약해짐 |

(3)은 권하지 않는다. `EP-1`이 이미 검정력 0.65이고 §7.2가 그것을 사전 고지한 상태에서
표본을 더 깎으면 주 엔드포인트가 무의미해진다.

### 에이전트 의견

**(1)을 권한다.** `ES-2`는 "정렬 기반 점수가 **실무 기본값**을 이기는가"이고,
§5.1b가 "감사 파이프라인의 진짜 경쟁 상대는 실무 기본값"이라고 못박은 만큼
`H2`에서 가장 중요한 비교다. 그리고 대상 셀이 **오늘 확정되어 있어 불확실성이 0**이다.
+30 trial(약 1.3시간)로 가장 중요한 비교 하나를 확정적으로 사는 셈이다.

`ES-1`/`ES-3`는 (4)처럼 "계산 가능할 때만 보고"로 사전 약정하되,
`arms.coverage_report()`가 `LOCK-2` 시점에 가능 여부를 자동 기록한다.

`src/edgeqgate/arms.py`의 `coverage_report()`가 이 상태를 자동 보고한다.
실기 종료 후 발견하면 사후 trial 추가는 `IG-4`/`IG-5`를 깨뜨려 방법이 없다.

## 3. `VC-025`(FP16) 순위 풀 처리

**왜 사람이**: §5.2/§7.1 변경이며 연구 질문의 범위를 정하는 결정이다.

**측정된 사실** (`attempt-013`, `attempt-014`): 같은 체크포인트·같은 16상태에서

| | `score_mag` | CI95 (부트스트랩 200) |
|---|---|---|
| INT8 | 0.02058 | [0.02019, 0.02092] |
| FP16 | 0.00225 | [0.00219, 0.00229] |

**CI가 겹치지 않는다.** FP16이 INT8보다 오차가 약 8–9배 작다. §5.2가 25셀을 한 순위에
놓으면 `VC-025`가 압도적 1위가 되고 §7.1의 `ARM-AUDIT`(상위 3셀)을 잠식한다.
그러면 `EP-1`의 상당 부분이 "감사기가 FP16을 골랐다"는 자명한 사실에서 나온다.

**선택지**: 순위 풀에서 제외 / 풀에 두되 `ARM-AUDIT` 선정에서 제외 /
그대로 두고 `EP-1`을 FP16 포함·제외 양쪽으로 보고

참고: 초기에 "FP16이 실무적으로 더 나은 선택일 수 있다"는 논거가 있었으나,
`--int8 --fp16` 재빌드 후 INT8이 FP16보다 **1.19배 빠르고 엔진이 36% 작다**는 것이
확인되어(`attempt-013`) 그 논거는 성립하지 않는다.

## 4. §9.3 감사 지표 출처 — 공개 범위 확인

**왜 사람이**: 사전등록 문서 자체가 "내가 판단할 사안 아님"으로 명시한다.

**현황**: 구현은 §12가 지정한 회피 경로(진행도 회귀기 기반 투영)만 쓰고 있어
기존 미발표 연구의 원 지표를 참조하지 않는다. 이 선택은 확인 결과와 무관하게 안전하다.

**그러나 확인 의무는 남는다**: 리포지토리가 현재 private이지만 `D1`이 제출 시점에
**공개 Apache 2.0 리포**를 요구한다. 즉 **2026-10-30 공개 전환이 선행공개 시점**이다.
진행 중인 학회 제출과의 중복·선행공개 문제를 그 전에 확인해야 한다.

## 5. §5.3 팬아웃 구조 개정

**왜 사람이**: 사전등록된 작업 단위 정의의 변경이다.

**측정된 사실** (`attempt-007`, `attempt-014`):

| | |
|---|---|
| 셀당 실연산 (부트스트랩 200회 포함) | **0.059초** |
| 잡당 플랫폼 오버헤드 | **261초** |
| `compute.instance.count` 쿼터 (동시성 상한) | **12** |

| 구성 | 잡 수 | 오버헤드 총합 | 실연산 총합 |
|---|---|---|---|
| §5.3 원안 (셀 × replicate) | 5,200 | **31.5시간** | 1.5초 |
| 셀 단위 | 26 | 0.22시간 | 1.5초 |

부트스트랩은 같은 오차 벡터 위의 재표집이므로 잡 경계를 나눌 계산상의 근거가 없다.

**묶든 나누든 같은 값**이 나온다(테스트로 고정되어 있다).

## 6. 지그·조명·오버헤드 마운트 (`G1`)

물리 작업. §2.3의 재현성 고정 장치 — 지그 위치 마킹·사진 기록, 팔 베이스 마킹,
조명 고정. **촬영용 조명 변경은 이후 모든 trial을 무효화하므로 촬영은 데이터 수집 완료 후.**

배선 권고 (Jetson USB 토폴로지 실측 기반, `attempt-013` 후속):

| 장치 | 연결 | 이유 |
|---|---|---|
| 팔로워 USB-TTL | Jetson USB 2.0 | 서보 트래픽 ~1 Mbps |
| 리더 USB-TTL | Jetson USB 2.0 (수집 전용) | 동일 |
| 손목 웹캠 | Jetson **USB 3.0 (Bus 02)** + MJPEG 강제 | YUYV면 2.0 버스 포화 |
| 오버헤드 | Jetson **CSI** | Orin Nano에 CSI 2포트, 현재 비어 있음 |
| RealSense / Luxonis | **GB10** | 판정용은 제어 루프 밖. Jetson USB 경쟁 회피 |

Jetson USB 실측: Bus 02가 USB 3.0(10 Gbps), Bus 01이 USB 2.0(480 Mbps),
외부 Type-A 4포트가 버스당 허브 하나를 공유한다.

## 8. `calib_size=1024` 가능 여부 (`G1` 직후)

드라이런에서 프레임 풀이 408개라 `calib_size=1024` 셀 6개가 전부 "전체 408개"를 뽑아
동일해졌다(캘리브레이션 세트 24개 중 고유 19개, `attempt-011`).

실제 train 80 에피소드에서 1024 프레임을 **중복 없이** 뽑을 수 있는지 확인해야 한다.
불가능하면 축 수준 조정이 필요하고, 그 개정은 **데이터 수집 직후·점수 산출 전**에 해야 한다.

## 9. 수집 호스트 프레임 드롭률 (`G1`)

Jetson에서 텔레옵 수집 시 2카메라 × 30fps 인코딩 + 서보 IO를 감당하는지.
드롭이 심하면 GB10 수집으로 전환하되, **카메라 설정(해상도·포맷·노출 고정)을 동일하게**
맞춰야 학습/배포 관측 분포가 어긋나지 않는다.

`docs/success_criterion.md`가 "프레임 손실 → 무효 trial"로 정의하고 무효율 5% 초과 시
보고하도록 되어 있어, 이것이 순전히 USB 대역폭 때문에 터질 수 있다.

## 11. 정책을 LeRobot ACT로 전환할지

**왜 사람이**: §9.1(정책 아키텍처)에 걸린 결정이다.

**현황**: 지금 파이프라인은 `scripts/act_model.py` — 위상만 맞춘 **손으로 만든 근사**다.
`K4` 검증에는 충분했지만 본 실험의 정책으로는 약하다.

Nebius 쿡북의 `robotics/lerobot-finetune-job` 레시피가 LeRobot ACT 학습을 제공하고,
**실제 LeRobot ACT가 우리 export 경로를 전 구간 통과함을 확인했다**(attempt-018):
ONNX 138MB → modelopt INT8 → TRT FP16/INT8 빌드 모두 성공.

| | 손으로 만든 것 | LeRobot ACT |
|---|---|---|
| 파라미터 | 78.0 M | 51.6 M |
| FP16 엔진 | 158 MB | 74 MB |

**전환 비용**: `G0` export 검증과 26셀 빌드 재실행. 지금까지의 지연·크기 실측값은
전부 손으로 만든 모델의 것이라 다시 재야 한다.

**지금이 가장 싼 시점**: 데이터 수집 전, `LOCK-2` 동결 전이라 사전등록 위반 없이 바꿀 수 있다.

**전환 시 주의**
- 레시피 예제의 `--platform gpu-h100-sxm`($3.85/h) 대신 `gpu-l40s-a`($1.55/h)
- **`--preemptible` 금지** — `IG-3`가 단일 체크포인트를 요구한다
- 레시피 이미지는 lerobot **0.5.1**, 로컬 검증은 **0.6.1**. 버전을 맞춰야 한다

## 12. 양팔(bimanual) 태스크로 전환할지

**왜 사람이**: §2.1(태스크 정의) 변경이며, 장비 조달과 일정 판단이 걸린다.

**선행 조건**: SO-101 **리더+팔로워 2세트(4대)**. 리더-팔로워 텔레옵으로 양팔을 하려면
리더 2 + 팔로워 2가 필요하다. §2.2는 현재 한 쌍만 잡고 있다. *(확인 중)*

### 확인된 것 (attempt-019)

**툴체인 비용이 0이다.** 6-DoF와 12-DoF가 파라미터·ONNX·엔진·Q/DQ 노드까지 동일하며
FP16/INT8 빌드가 모두 성공한다. Orin 지연 실측, 26셀 그리드, 감사 파이프라인이 그대로 유효하고
**Jetson 한 대로 충분하다**(정책 하나가 12-DoF를 낸다).

ACT의 정본 태스크가 양팔이라는 점도 유리하다 — ALOHA는 14-DoF다.

**`H2` 강화 논거는 조건부다.** 합성 검증 결과 "차원이 늘면 `score_align` 우위가 커진다"는
세 시나리오 중 둘에서 성립하고, 민감 부분공간이 차원에 비례해 커지는 경우 무너진다.
효과 크기 추정도 불안정하다. **가능성이지 보장이 아니다.**
